# v3.4.4 : l'assemblage passe derrière un sous-domaine chiffré

Deux applications Keneya cohabitent sur le serveur, et jusqu'ici elles
n'étaient pas rangées de la même façon. Cette note décrit le partage retenu et
ce qu'il a fallu changer dans l'application pour qu'il tienne.

---

## 1. Ce qui existait

| | Avant |
|---|---|
| `keneya.sukaxess.com`, HTTPS | `/var/www/keneya-workflow` — dépôt `keneya_workflow`, servi par Apache |
| `161.97.183.94:8083`, en clair | l'assemblage — dépôt `-keneya_wf-mod`, pile Docker |

L'assemblage, celui qui porte le module DME, n'avait ni domaine ni certificat.
Le projet d'origine, lui, occupait le seul sous-domaine en service. Deux fois
en une journée, une commande de mise à jour est partie dans le mauvais
dossier : les deux installations portent des noms voisins, dans deux
arborescences différentes, et rien sur place ne disait laquelle servait quoi.

## 2. Le partage retenu

**Un sous-domaine chacune**, chacun avec son certificat. Aucune des deux
n'est en production — le projet est en construction — mais servir une
application de santé en clair, même en démonstration, installe une habitude
dont on ne se défait pas au moment de la mise en service.

| | Après |
|---|---|
| `keneya.sukaxess.com` | l'assemblage, relayé par Apache vers la pile Docker |
| un second sous-domaine | `/var/www/keneya-workflow`, servi par Apache comme aujourd'hui |

## 3. Ce que l'application a dû apprendre

### Faire confiance au proxy

Derrière un proxy qui termine le TLS, la pile ne voit qu'une requête HTTP
ordinaire. Sans instruction, Laravel fabrique donc des URL en `http://` dans
une page servie en `https://` — et le navigateur bloque la feuille de style,
les images et les appels Livewire. **La page s'affiche cassée sans que rien
n'en dise la cause**, ce qui est le plus long à diagnostiquer.

`bootstrap/app.php` déclare désormais les plages privées et la boucle locale
comme proxys de confiance. Pas `*` : un en-tête `X-Forwarded-Proto` se
falsifie, et le croire sur parole de n'importe quelle source laisserait un
visiteur faire passer sa requête pour chiffrée.

Vérifié en simulant le proxy :

```
avec en-têtes    href="https://keneya.sukaxess.com/css/app.css"
sans en-têtes    href="http://localhost:8083/css/app.css"
```

### Cesser d'être joignable en direct

La confiance accordée au proxy n'a de sens que si le proxy est **le seul** à
pouvoir parler à la pile. `docker-compose.yml` publie donc sur
`${APP_HTTP_BIND:-127.0.0.1}` : par défaut la boucle locale.

Deux raisons, et la seconde est la plus sérieuse. Le site ne reste pas
accessible en clair à côté du domaine chiffré ; et surtout, personne de
l'extérieur ne peut envoyer un faux `X-Forwarded-Proto` à une pile qui a pour
consigne d'y croire.

`APP_HTTP_BIND=0.0.0.0` rouvre l'accès direct, pour une machine de
développement ou une pile sans proxy devant.

### Deux réglages du `.env`

```
APP_URL=https://keneya.sukaxess.com
SESSION_SECURE_COOKIE=true
```

Sans le premier, les liens des SMS — « mes documents », le lien du portail
patient — partent vers `localhost` et ne mènent nulle part. Sans le second, le
cookie de session voyage sans sa marque « chiffré seulement ».

## 4. Ce qui reste à décider avant d'ouvrir

**Les comptes de démonstration.** L'assemblage est semé avec
`admin@keneya.local` et un mot de passe qui figure dans le dépôt. Sur une
adresse IP sans domaine, c'était imprudent mais discret. Sur un sous-domaine
en HTTPS, c'est trouvable : n'importe qui pourra se connecter en
administrateur. Changez `SEED_DEFAULT_PASSWORD` avant d'ouvrir, ou restreignez
l'accès.

## 5. La marche à suivre

Le gabarit d'hôte virtuel est dans `deploy/apache/keneya-assemblage.conf`, avec
ses prérequis. En résumé :

```bash
sudo a2enmod proxy proxy_http headers
sudo a2ensite keneya-assemblage
sudo apache2ctl configtest && sudo systemctl reload apache2
sudo certbot --apache -d keneya.sukaxess.com
```

Le DNS doit pointer sur le serveur **avant** : certbot vérifie la
correspondance depuis l'extérieur, et tant que la propagation n'est pas faite
il refuse d'émettre — avec un message qui parle de validation, jamais de DNS.
