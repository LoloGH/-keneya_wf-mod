# v3.4.2 : le module DME entre dans le dépôt

Le module `keneya/dme` vivait dans un dépôt voisin, monté par un dépôt Composer
de type `path` à l'adresse `../keneya-dme_mod`. Il vit désormais **dans ce
dépôt**, sous `modules/dme`.

---

## 1. Pourquoi

Deux dépôts pour une seule application, c'était une bonne façon de les écrire
et une mauvaise façon de les exploiter.

**Le défaut principal ne se voyait pas.** Mettre à jour l'un sans l'autre ne
produisait aucune erreur franche : l'application démarrait, servait ses pages,
et se comportait mal à l'endroit précis où le code d'un côté appelait ce qui
n'existait pas encore de l'autre. C'est la panne la plus coûteuse à
diagnostiquer, parce qu'elle ne ressemble pas à un problème de déploiement.

**La CI ne protégeait pas de cela.** Elle clonait deux dépôts sur deux
références distinctes — le second sur une branche nommée en dur dans le
workflow. Verte, elle ne prouvait pas que les deux moitiés avançaient
ensemble ; seulement qu'elles s'entendaient à l'instant du clone.

**Et le coût se payait à chaque geste.** Une mise à jour du serveur, faite à la
main, a demandé seize commandes ; deux d'entre elles servaient uniquement à
tenir le second dépôt sur la bonne branche.

## 2. Ce qui a été fait

L'historique du module a été repris par `git subtree`, pas recopié : ses
commits, leurs auteurs et leurs messages sont dans ce dépôt.

Le dépôt [`LoloGH/-keneya-dme_mod`](https://github.com/LoloGH/-keneya-dme_mod)
reste en place, figé à `2428ead` sur `assemblage-workflow` — l'état repris ici.
**Le développement du module continue dans ce dépôt-ci**, plus là-bas.

## 3. Ce que le déplacement supprime

Trois contournements existaient uniquement parce que le module était ailleurs.

**Le `composer.json` bidon du `Dockerfile`.** L'adresse du module était vide
pendant le build — le montage n'existe qu'au démarrage — et composer refusait
d'installer quoi que ce soit. L'image fabriquait donc un `composer.json`
minimal à cette adresse, que le montage remplaçait ensuite. Onze lignes
remplacées par deux : `COPY modules/dme/composer.json`, avant l'installation
des dépendances, pour que la couche ne soit pas invalidée dès qu'une vue du
module change.

**Le second `safe.directory`** déclaré dans l'image, `modules/dme` étant
désormais sous `/var/www/html`, déjà déclaré.

**Le second `checkout` de la CI**, et la branche nommée à la main qui allait
avec.

Les trois montages `../keneya-dme_mod:/var/www/keneya-dme_mod:ro` disparaissent
aussi : le module arrive avec `./:/var/www/html`.

## 4. Ce que le déplacement change, et qu'il faut savoir

**Le module n'est plus monté en lecture seule** pour les services qui servent
l'application. Il l'était, délibérément : une pile qui répond à des requêtes
HTTP n'a aucune raison de pouvoir réécrire le code d'un de ses paquets. Il est
maintenant dans `./`, aussi accessible en écriture que le reste du code de
l'application — ni plus, ni moins. La protection était réelle mais partielle,
et la maintenir aurait demandé un montage dédié qui recréait la complexité
qu'on venait de retirer.

**Le service `dme` reste.** Le module garde sa propre suite de tests, et elle
dit autre chose que celle de l'hôte : celle-ci le traverse, mais toujours avec
WorkFlow derrière, tandis que la sienne le vérifie **seul**, sans hôte pour lui
fournir un utilisateur, des rôles ou une signature. Un câblage manquant passe
la première et échoue la seconde. Son `working_dir` devient
`/var/www/html/modules/dme`.

`COMPOSER_PROCESS_TIMEOUT: 0` lui est ajouté : `composer install` écrit
quelques milliers de fichiers dans `modules/dme/vendor`, sur un montage venant
de l'hôte, et le délai de 300 s que composer s'impose par défaut est atteint
avant la fin — l'erreur parle alors d'un processus expiré, jamais du montage.

## 5. Les deux styles, et les deux suites

Le module n'avait jamais été soumis au Pint de l'hôte : celui-ci ne regardait
pas le dossier voisin. Une fois le module dans le dépôt, `vendor/bin/pint
--test` l'a trouvé et a rendu **114 infractions** — non pas parce que le module
est mal écrit, mais parce qu'il suit ses propres conventions, à commencer par
`declare(strict_types=1)`.

Reformater ces 114 fichiers aurait noyé un commit d'architecture sous du bruit
et détruit le `git blame` du module pour un gain nul. Un `pint.json` l'exclut
donc du formateur de l'hôte, et **chaque côté garde le sien** :

| | Formateur | Tests |
|---|---|---|
| Hôte | `vendor/bin/pint` (préréglage Laravel, `modules/dme` exclu) | 738 |
| Module | `modules/dme/vendor/bin/pint` | 257 |

Et la CI gagne un second job. **La suite du module n'y avait jamais tourné** :
elle vivait dans un autre dépôt, avec son propre outillage, et personne ne la
déclenchait. La raison a disparu avec le dossier voisin. Elle n'a besoin
d'aucun service de base — Testbench, SQLite en mémoire — et couvre ce que celle
de l'hôte ne peut pas voir : le module **seul**, sans hôte pour lui fournir un
utilisateur, des rôles ou une signature.

## 6. Ce que ça donne

```bash
git clone https://github.com/LoloGH/-keneya_wf-mod.git
cd keneya_wf-mod
./install.sh
```

Et pour une mise à jour :

```bash
./scripts/update.sh
```

`scripts/update.sh` perd toute sa logique à deux dépôts : plus de second
`pull`, plus de branche à nommer, plus de vérification croisée.
